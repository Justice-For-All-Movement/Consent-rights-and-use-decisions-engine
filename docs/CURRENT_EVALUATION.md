# Current-time permission evaluation

`PermissionRegistry.evaluateCurrent(context, resourceRef, request, ids, clock)` is an opt-in owning-registry read. The trusted synchronous host clock returns a timestamp string. The adapter captures ordinary JSON inputs, checks scoped read authority and explicit bounded permission ID arrays, acquires its own project lock, then loads the actual registered resource and current requested rights/consent editions. It samples the clock only after those reads and passes that time to the existing exact-use decision function. No caller-supplied permission objects or resource consent requirements replace stored records.

The clock must return a valid string at most128 characters long, at or after the captured request time. Missing, throwing, non-string, asynchronous, malformed or regressed clock results fail with `clock_unavailable` and a sanitized message. A failed evaluation rolls back its checked audit. The clock is host policy, not network time authentication; it must be synchronous and must not start background work. SQL begins under the existing SDK transaction rules and may outlive a host request. Missing acknowledgement is unknown, never rollback or a usable decision.

The legacy `evaluate` method retains request-time semantics and its existing signature. Hosts must explicitly select `evaluateCurrent` when they require time after database waits. `checkedAt` is the observed decision time; the SDK audit envelope still records request metadata, not an invented SQL commit time. The decision/hash audit commits with the read. No permission revision, command cache or effect outbox is created by evaluation.

An allowed decision describes observed stored permission records at the sampled time. It is not a future execution permit, a legal consent/rights ownership attestation, an Identity lookup or an atomic revocation fence across another engine. A permission may expire or be withdrawn immediately afterward, including while the audit or COMMIT acknowledgement is pending. Consumers must authenticate actors, enforce current purpose/resource policy and choose the applicable action/audience/attribution; metadata citation does not authorize copying, training or distribution. The host remains responsible for current roles, subject mappings, clock integrity, ingress/CPU/heap/driver deadlines, TLS and deployment acceptance. There is no listener, provider dispatch, publication or payment route.

## Verification scope

Five new groups apply the actual stable SDK migration under a restricted PGlite login. Instrumented actual lock and record queries advance the clock after the lock or final permission read, compare the explicit legacy result, exercise input capture, sanitized invalid clocks/rollback and scoped admission, and retain current withdrawal after a lost real read-transaction acknowledgement. These hooks are embedded ordering evidence, not independent network sessions. The existing six PostgreSQL17 CI scenarios remain separate and unchanged. Production clock/identity/rights qualification, remote TLS, crash/failover, browser/assistive technology and live acceptance remain pending.
